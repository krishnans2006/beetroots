# Beetroots implementation plan

Build a Python wrapper around the beets singleton autotagger. Its public operation is `Matcher.match(track) -> MatchResult`. A caller can supply as little as a recording MBID, a provider URL, or an artist and title. Beetroots returns the best candidate’s proposed tags, confidence, and identification method in a separate result. The caller decides whether to apply those tags and can make that decision using saved results. Each call is independent, so the same raw listen can also be processed again under a different matcher configuration.

### 1. Public interface

Provide a typed `TrackInput` and a `beetroots match` command that reads and writes one JSON object per line. Both entry points use the same schema. A minimal input is `{"title":"Teardrop","artist":"Massive Attack"}`. Drivers can attach a `record_id` to associate the result with the original listen.

| Optional input | How beetroots uses it |
|---|---|
| Title, alternate titles, display artist, ordered artist credits, album, album artists, version or disambiguation | Search for recordings and distinguish versions. Accept an unsplit artist string directly. Preserve structured credits when supplied. |
| Recording, release-track, release, release-group, artist and work MBIDs | Resolve the entity each ID identifies. A release-track ID identifies a particular appearance of a recording. Artist, work and release-group IDs narrow the candidates. |
| ISRCs, Spotify track ID or URI, YouTube video ID, source URLs | Find linked recordings or retrieve provider metadata. Keep provider identifiers in their own namespaces. |
| Full duration in milliseconds, disc and track positions, release date, country, format, label, catalog number and barcode | Narrow recording searches or distinguish editions when the corresponding evidence exists. Preserve partial dates. |
| Source, listened-at timestamp, elapsed playback time and arbitrary driver context | Carry these through for correlation. Only full track duration participates in duration scoring. |

These fields cover the distinctions present in ListenBrainz, provider track metadata, and MusicBrainz recording and release searches. Native export readers, Koito storage, and a cross-record Navidrome catalog belong to future drivers. [ListenBrainz listen schema](https://listenbrainz.readthedocs.io/en/latest/users/json.html) · [MusicBrainz search fields](https://musicbrainz.org/doc/MusicBrainz_API/Search) · [Spotify streaming-history fields](https://support.spotify.com/sg-en/article/understanding-your-data/)

### 2. Recording resolution

1. **Honor supplied MBIDs first.** Resolve a recording MBID directly and follow MusicBrainz merges to the current ID. Resolve a release-track MBID to its recording and edition. A verified identity wins even when every text tag disagrees. Report malformed, unresolvable, or conflicting authoritative IDs explicitly. If the recording is verified and only the release conflicts, return the recording tags and flag the release conflict. [MusicBrainz recording model](https://musicbrainz.org/doc/Recording) · [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API)
2. **Enrich from provider IDs.** When configured, fetch Spotify’s track metadata using client credentials. For YouTube Music, use `ytmusicapi` and take the watch entry whose video ID equals the requested ID. Use the returned title, ordered artists, album, duration, track position and ISRC where available. Keep supplied and fetched values distinguishable so a driver can explain a disagreement. If a provider is unavailable, continue with usable input evidence. [Spotify Get Track](https://developer.spotify.com/documentation/web-api/reference/get-track) · [Spotify client credentials](https://developer.spotify.com/documentation/web-api/tutorials/client-credentials-flow) · [YouTube Music watch metadata](https://ytmusicapi.readthedocs.io/en/stable/reference/watch.html)
3. **Let beets find and rank recordings.** Pin the locally available beets 2.14.1 for the first implementation. Construct an in-memory `Item` and `Source.from_item()`. Use the MusicBrainz plugin for ordinary singleton searches and tag extraction. Supplement its artist/title query with candidate IDs from ISRCs, MusicBrainz URL relationships, and supplied release or artist constraints. Deduplicate by recording MBID and rank candidates using beets’ singleton distance and ordering. Internally fix `match.strong_rec_thresh` at `0` to disable beets’ strong-match shortcut. Select the first scored candidate directly. Preserve meaningful qualifiers such as *live*, *remix* and *acoustic*. Return MusicBrainz’s ordered artist credits and display credit, which also handles names containing commas or ampersands. [beets singleton matcher](https://github.com/beetbox/beets/blob/v2.14.1/beets/autotag/match.py) · [beets MusicBrainz plugin](https://github.com/beetbox/beets/blob/v2.14.1/beetsplug/musicbrainz.py)
4. **Score only observed metadata.** Use a comparison copy that omits unavailable evidence while retaining the complete candidate for output. I verified the need for this against the installed beets version: an exact artist/title match against a 200-second recording scored distance `0.286` when the input lacked duration. Omitting the unavailable comparison gave distance `0.0`. If there is no comparable metadata or verified identity, return insufficient evidence. [beets distance implementation](https://github.com/beetbox/beets/blob/v2.14.1/beets/autotag/distance.py)

### 3. Results, release selection and replay

- **Confidence.** For a verified recording or release-track MBID, return `confidence: 1.0` and the identity method. For every scored metadata match, return the top candidate’s proposed tags, its distance, and `confidence = 1 - float(distance)`. The score measures metadata similarity. Return that candidate even when its confidence is zero. For ties, return the first in beets’ ordering. When no candidate can be scored or verified, return null confidence and null proposed tags alongside the reason. [beets matching configuration](https://beets.readthedocs.io/en/stable/reference/config.html)
- **Corrected tags.** Return recording title, display artist, ordered artist names and MBIDs, recording MBID, duration and ISRCs where available. Use an authoritative release or release-track ID first. Otherwise use the supplied edition evidence, including album title and track position. If several editions still fit, choose an official release first, then the earliest known release date, then release MBID for a stable tie-break. Mark that choice `inferred`. Fetch album title, album artists, release and release-group MBIDs, date, disc and track from the selected edition. Recording confidence remains independent of edition selection. This fallback is needed because beets’ MusicBrainz singleton lookup returns recording metadata without selecting an edition. [beets MusicBrainz plugin](https://github.com/beetbox/beets/blob/v2.14.1/beetsplug/musicbrainz.py) · [MusicBrainz release model](https://musicbrainz.org/doc/Release)
- **Replay and batch behavior.** Emit one result per input in order, including invalid records and lookup failures. Include the record ID, method, matcher version and effective configuration fingerprint. Use a refreshable persistent lookup cache so repeated listens and changes to scoring weights can reuse provider responses. Honor MusicBrainz rate limits and distinguish temporary failures from completed searches with zero candidates. [MusicBrainz rate limits](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)

### 4. Acceptance tests

Use the real pinned beets matcher with recorded provider responses. Verify these cases through both the Python API and JSON Lines CLI.

- A trusted Navidrome-style MBID with incorrect text returns canonical tags. Cover a merged MBID, a release-track-only input, conflicting IDs, and an unavailable MusicBrainz service.
- A Spotify URI alone and a YouTube Music URL alone can resolve through enrichment. Cover missing ISRCs, deleted videos, multi-artist credits, and partial playback time.
- An exact artist/title pair works without duration. A fixture with studio and live versions uses the supplied version or release evidence. Tied candidates follow beets’ ordering.
- A fixture whose best candidate has distance `1.0` returns that candidate’s recording MBID, proposed tags and confidence `0.0`. A search with zero candidates returns null proposed tags and null confidence.
- The same recording on several editions produces an identified or explicitly inferred release. Every selected release track points back to the returned recording.
- Replaying identical inputs against the same cached responses and configuration produces identical match results. Duplicate listens retain separate outputs, malformed rows do not interrupt the batch, and the original inputs remain byte-for-byte intact.
