# Beetroots implementation plan

Build a Python wrapper around the beets singleton autotagger. Its public operation is `Matcher.match(track) -> MatchResult`. A caller can supply as little as a recording MBID, a provider URL, or an artist and title. Beetroots first chooses an MBID and records its identification method and confidence. Once chosen, the MBID is treated as correct for that result. Beetroots retrieves the MusicBrainz metadata for that identity and returns it alongside proposed tags in a separate result. The caller decides whether to apply those tags and can make that decision using saved results. Each call is independent, so the same raw listen can also be processed again under a different matcher configuration.

### 1. Public interface

Provide a typed `TrackInput` and a `beetroots match` command that reads and writes one JSON object per line. Both entry points use the same schema. A minimal input is `{"title":"Teardrop","artist":"Massive Attack"}`. Drivers can attach a `record_id` to associate the result with the original listen.

| Optional input | How beetroots uses it |
|---|---|
| Title, alternate titles, display artist, ordered artist credits, album, album artists, version or disambiguation | Search for recordings and distinguish versions. Accept an unsplit artist string directly. Preserve structured credits when supplied. |
| Recording, release-track, release, release-group, artist and work MBIDs | Resolve the entity each ID identifies. A release-track ID identifies a particular appearance of a recording. Artist, work and release-group IDs narrow the candidates. |
| ISRCs, Spotify track ID or URI, YouTube video ID, source URLs | Find linked recordings or retrieve provider metadata. Keep provider identifiers in their own namespaces. |
| Full duration in milliseconds, disc and track positions, release date, country, format, label, catalog number and barcode | Narrow recording searches or distinguish editions when the corresponding evidence exists. Preserve partial dates. |
| Source, listened-at timestamp, elapsed playback time and arbitrary driver context | Carry these through for correlation. Only full track duration participates in duration scoring. |

These fields cover the distinctions present in ListenBrainz, provider track metadata, and MusicBrainz recording and release searches. Native export readers, Koito storage, and a cross-record Navidrome catalog belong to future drivers. [ListenBrainz listen schema](https://listenbrainz.readthedocs.io/en/latest/users/json.html) · [MusicBrainz search fields](https://musicbrainz.org/doc/MusicBrainz_API/Search) · [Spotify streaming-history fields](https://support.spotify.com/sg-en/article/understanding-your-data/)

### 2. Choose the MusicBrainz identity

1. **Honor supplied MBIDs first.** Resolve a recording MBID directly and follow MusicBrainz merges to the current ID. Resolve a release-track MBID using MusicBrainz recording search by `tid`, then verify the exact track MBID and its recording in the release tracklist. Retain that track occurrence even when the recording appears more than once on the release. Pass only recording MBIDs to beets’ `track_for_id`. A verified identity wins even when every text tag disagrees. Report malformed, unresolvable, or conflicting authoritative IDs explicitly. If the recording is verified and only the release conflicts, choose the recording MBID and flag the release conflict. [MusicBrainz recording model](https://musicbrainz.org/doc/Recording) · [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API)
2. **Enrich from provider IDs.** When configured, fetch Spotify’s track metadata using client credentials. For YouTube Music, use `ytmusicapi` and take the watch entry whose video ID equals the requested ID. Use the returned title, ordered artists, album, duration, track position and ISRC where available. Keep supplied and fetched values distinguishable so a driver can explain a disagreement. If a provider is unavailable, continue with usable input evidence. [Spotify Get Track](https://developer.spotify.com/documentation/web-api/reference/get-track) · [Spotify client credentials](https://developer.spotify.com/documentation/web-api/tutorials/client-credentials-flow) · [YouTube Music watch metadata](https://ytmusicapi.readthedocs.io/en/stable/reference/watch.html)
3. **Let beets find and rank recordings.** Pin the locally available beets 2.14.1 for the first implementation. Construct an in-memory `Item` and `Source.from_item()`. Use the MusicBrainz plugin for ordinary singleton searches and tag extraction. Supplement its artist/title query with candidate IDs from ISRCs, MusicBrainz URL relationships, and supplied release or artist constraints. Collect ordinary text and supplemental candidates separately because `tag_item(search_ids=...)` skips text search. Merge ordinary text results in provider order, then append supplemental candidates in recording MBID order. Deduplicate by canonical recording MBID, keeping the first position and enriching the candidate with evidence from all sources. Set beets’ `raise_on_error` and handle lookup failures at the wrapper boundary. Retain usable candidates and report failed lookup paths in the result. Preserve meaningful qualifiers such as *live*, *remix* and *acoustic*. Use explicit version evidence against candidate titles and disambiguation, and edition evidence against verified release appearances, to exclude known mismatches when at least one candidate positively matches the same evidence. Keep candidates with unknown values eligible. Rank eligible candidates by beets’ singleton distance using its stable ascending order and select the first scored candidate’s recording MBID. Resolve edition evidence during this stage. Carry forward a release or track occurrence identified from MusicBrainz and verified to contain the chosen recording. [beets singleton matcher](https://github.com/beetbox/beets/blob/v2.14.1/beets/autotag/match.py) · [beets MusicBrainz plugin](https://github.com/beetbox/beets/blob/v2.14.1/beetsplug/musicbrainz.py)
4. **Score only observed metadata.** Use beets’ singleton comparison rules and distance weighting for title, artist, full duration, and disc and track positions. Include each component only when both sides have the relevant value and its weight is positive. Use a comparison copy or explicitly build the eligible distance components where omission alone cannot suppress a penalty, as with title. Use the comparison only to choose the MBID. With beets 2.14.1, omitting an unavailable duration comparison changes the distance for an exact artist/title pair from `0.286` to `0.0`. An omitted input title still incurs a title penalty in the stock matcher, and an empty beets distance evaluates to zero. Require at least one eligible comparison before using the distance. A URL relationship or ISRC can supply candidates, including a unique candidate, and the same comparison requirement applies. When candidates exist but none can be compared and no authoritative MBID verifies identity, return `insufficient_evidence`. [beets distance implementation](https://github.com/beetbox/beets/blob/v2.14.1/beets/autotag/distance.py)

### 3. Retrieve metadata for the chosen MBID

- **Confidence.** For a verified recording or release-track MBID, return `confidence: 1.0` and the identity method. For every scored metadata match, return the chosen recording MBID, its distance, and `confidence = 1 - float(distance)`. Confidence describes how the MBID was chosen. Retrieve the same MusicBrainz metadata for the chosen identity at every confidence, including zero. For ties, return the first in the stable order established when merging candidates. When no candidate can be scored or verified, return null confidence and null proposed tags alongside the reason. [beets matching configuration](https://beets.readthedocs.io/en/stable/reference/config.html)
- **Canonical metadata.** Once an MBID is chosen, end matching and retrieve the full MusicBrainz recording, following merges to the current ID. Fetch every available field and page of related data for that identity. Include all linked release appearances and their release groups, the complete ordered artist credits with join phrases, works and other relationships, aliases, ISRCs, dates, durations, and other metadata the API exposes. Preserve the full entity payloads and relationships in the result so fields outside the proposed tag schema are available to callers. Fetch linked entities that supply metadata for the identified recording and its appearances. Keep relationship references to the rest of the MusicBrainz graph. [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API) · [MusicBrainz recording model](https://musicbrainz.org/doc/Recording)
- **Proposed tags.** Derive every tag from the retrieved MusicBrainz entities. Use the recording for recording-level tags and its verified release appearance for edition-level tags. Use an edition or exact track occurrence established during identification when available. Otherwise, if linked editions exist, infer one from the MusicBrainz data by preferring official releases, then the earliest known release date, then release MBID. Sort known dates by recorded year, month and day, with missing components first at their position and undated releases last. If the recording appears more than once on the selected edition, use the verified occurrence when available and otherwise take the first in medium and track order. Mark an inferred edition as such and keep all retrieved appearances in the metadata. Leave fields absent when MusicBrainz has no value. Keep caller and provider values in provenance only. [MusicBrainz release model](https://musicbrainz.org/doc/Release)

### 4. Replay and batch behavior

- **Determinism.** The same input, MusicBrainz and provider data, and effective matcher configuration must produce the same chosen MBID, release appearance, confidence, identification method, metadata and proposed tags, regardless of cache state or lookup completion order.
- **Replay and batch behavior.** Emit one result per input in order, including invalid records and lookup failures. Include the record ID, method, matcher version and effective configuration fingerprint. Use a refreshable persistent lookup cache so repeated listens and changes to scoring weights can reuse provider responses. Run beets in a separate worker process for each effective configuration so its process-wide cached scoring weights and duration thresholds remain isolated. Compute the fingerprint from the effective configuration applied by that worker. Share the lookup cache and MusicBrainz rate limiter across workers. Cache successful responses and completed empty lookups separately from temporary failures. [MusicBrainz rate limits](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)

### 5. Acceptance tests

Use the real pinned beets matcher with recorded provider responses. Verify these cases through both the Python API and JSON Lines CLI where applicable. Use the Python API for the test that holds two matcher instances in one caller process.

- A trusted Navidrome-style MBID with incorrect text returns canonical tags. Cover a merged MBID, a release-track-only input where the recording appears twice on the same release, conflicting IDs, and an unavailable MusicBrainz service on both ID lookup and text search.
- A Spotify URI alone and a YouTube Music URL alone can resolve through enrichment. Cover missing ISRCs, deleted videos, multi-artist credits, and partial playback time. A unique URL or ISRC candidate without comparable metadata returns insufficient evidence.
- An exact artist/title pair scores zero distance without duration. An artist-only input can score on artist without incurring a missing-title penalty. A candidate with no eligible comparisons yields null confidence. A fixture with studio and live versions uses the supplied version or release evidence. Text and supplemental candidate searches both run, and tied candidates follow the documented merge order.
- A fixture whose best candidate has distance `1.0` returns that candidate’s recording MBID, proposed tags and confidence `0.0`. A search with zero candidates returns null proposed tags and null confidence.
- A supplied MBID and a low-confidence match that choose the same MBID and edition return identical MusicBrainz metadata and proposed tags. Conflicting caller and provider values stay in provenance, and fields absent from MusicBrainz stay absent in the tags.
- The same recording on several editions returns every linked appearance, including those on subsequent response pages, and produces tags for the identified or explicitly inferred release. Every returned appearance points back to the chosen recording.
- Replaying identical inputs against the same provider data and configuration produces identical match results with cold and warm caches and different lookup completion orders. Duplicate listens retain separate outputs, malformed rows do not interrupt the batch, and the original inputs remain byte-for-byte intact.
